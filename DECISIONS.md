# Decisions

One entry per decision: what was chosen, the alternatives, and why. Newest at the bottom. Exact dependency versions are recorded here when a phase installs them.

## D-001 Browser extension as the delivery format

- **Chosen:** Chromium extension (Chrome, Edge, Opera GX).
- **Alternatives:** script snippet embedded in the site (like Marker.io); both.
- **Why:** works on any site without touching its code, including production sites the reviewer does not own. The snippet approach is kept as a post-MVP option because the demo page already needs an embed adapter.

## D-002 Comments anchor to an element or a text selection

- **Chosen:** two anchor kinds, `element` and `text`.
- **Alternatives:** element only; free-floating page coordinates.
- **Why:** element pins cover layout feedback, text anchors cover copy feedback. Page coordinates break on any layout change.

## D-003 Team workspaces with guest access

- **Chosen:** workspaces with owner, member and guest roles; guests join through an invite link with a display name only.
- **Alternatives:** personal local-only notes; local first, sync later.
- **Why:** the product is about collaboration with clients who will not create accounts.

## D-004 Supabase as the backend

- **Chosen:** Supabase (Auth, Postgres + RLS, Realtime, Storage, Edge Functions).
- **Alternatives:** Next.js API + Postgres (Neon) + NextAuth; Firebase.
- **Why:** realtime, auth, file storage and row-level security out of the box; local stack via Supabase CLI makes the whole app testable offline.

## D-005 Web app with landing, dashboard and demo

- **Chosen:** Next.js app with a landing page, dashboard, deep-link pages and a demo page that runs the widget without the extension.
- **Alternatives:** dashboard only; extension only.
- **Why:** people evaluating the project will not install an extension; the demo lets them try it in seconds.

## D-006 ClickUp: one-way task creation in MVP

- **Chosen:** create a ClickUp task from a thread, with a link back to the pin.
- **Alternatives:** full two-way status sync via webhooks in MVP; no integration in MVP.
- **Why:** delivers the main value with a fraction of the complexity; two-way sync is post-MVP.

## D-007 Tailwind 4 for styling

- **Chosen:** Tailwind 4 in both extension and web; compiled CSS injected into the extension's Shadow DOM.
- **Alternatives:** SCSS Modules + clsx.
- **Why:** one design system across both apps and faster iteration.

## D-008 Distribution decided after MVP

- **Chosen:** load unpacked during development; Chrome Web Store vs GitHub Release ZIP decided after MVP.
- **Why:** store review should not block building.

## D-009 Private repository until MVP

- **Chosen:** private GitHub repository, made public with a deployed demo and a README with a GIF.
- **Why:** the public profile should show a finished product, not an empty scaffold.

## D-010 pnpm workspace, Turborepo and internal packages consumed as source

- **Chosen:** pnpm workspaces (`apps/*`, `packages/*`, `e2e`) with Turborepo 2 for task orchestration. `packages/*` are private `@sitenote/*` packages whose `exports` point at `./src/index.ts`; they have no build step and are compiled by the consuming app's bundler (WXT, Next.js, Vitest). `@sitenote/ui` has no Tailwind build either: the consuming apps compile Tailwind 4 and add the package with `@source`. Dependency build scripts are gated by `strictDepBuilds: true` in `pnpm-workspace.yaml`, so an unreviewed install script fails the install; approvals go into pnpm 11 `allowBuilds`. No package needs one at the moment: `esbuild` was approved in step 1, but it is not in the lockfile (Vite 8 uses Rolldown, and neither Vitest 5, WXT 0.21 nor Next.js installs it), so the entry was removed together with the `allowBuilds` key. Root-level files (ESLint and Vitest configs, root `tsconfig.json`) are covered by Turborepo root tasks `//#lint:root` and `//#typecheck:root`, which every package `lint` and `typecheck` depends on.
- **Alternatives:** compiled packages (`tsup`/`tsc` build with `dist` exports); TypeScript project references; Nx; npm or yarn workspaces; `onlyBuiltDependencies` (older pnpm syntax).
- **Why:** source packages remove a build step and keep go-to-definition, HMR and tests pointing at real code. Turborepo is the lightest orchestrator that caches `lint`, `typecheck`, `test` and `build` per package. `allowBuilds` is the pnpm 11 mechanism and keeps installs deterministic and reviewable; an approval that matches no installed package is dead configuration and is removed.

## D-011 ESLint flat config, Prettier and named-exports enforcement

- **Chosen:** one root `eslint.config.js` with `typescript-eslint` `strictTypeChecked` and `stylisticTypeChecked`, `projectService: true`, `@typescript-eslint/no-explicit-any: error`, `eslint-plugin-react-hooks` (`recommended-latest`) for `*.tsx`, and `eslint-config-prettier` last. Named exports are enforced with the built-in `no-restricted-exports` (`restrictDefaultExports` all enabled), switched off only for `**/*.config.{ts,js,mjs}`, Next.js route files under `apps/web/src/app/**`, `apps/web/next.config.ts` and `apps/extension/entrypoints/**`. Plain `.js`/`.mjs` files use `disableTypeChecked`. ESLint 10 resolves the config from the linted file's directory upward, so running `eslint .` inside a package picks up the root config and no per-package config file is needed. Prettier uses `printWidth: 100`, double quotes, semicolons, trailing commas everywhere and LF endings. `README.md` and `docs/` are listed in `.prettierignore` because Prettier would rewrite their existing tables and wrapping; `DECISIONS.md` is formatted.
- **Alternatives:** `import/no-default-export` from `eslint-plugin-import` or `eslint-plugin-import-x`; Biome; per-package ESLint configs; `eslint-plugin-prettier`.
- **Why:** `no-restricted-exports` ships with ESLint and has the exact option set needed, so there is no extra plugin to keep in sync with ESLint 10. Prettier runs as a separate formatter instead of an ESLint rule to keep lint fast and diffs unambiguous. One root config avoids drift between packages.

## D-012 Vitest projects and happy-dom for component tests

- **Chosen:** Vitest 5 with the `test.projects` API. The root `vitest.config.ts` lists `apps/*/vitest.config.ts` and `packages/*/vitest.config.ts`; each package has its own config and a `test` script `vitest run`, which is what Turborepo runs. `@sitenote/core` runs in the `node` environment with `passWithNoTests: true`. `@sitenote/ui` runs in `happy-dom` with Testing Library, a setup file that calls `cleanup()` after each test, and no `@vitejs/plugin-react` because Vite 8 transforms JSX itself with the automatic JSX runtime.
- **Alternatives:** `jsdom`; Vitest browser mode for component tests; the deprecated `vitest.workspace` file; `globals: true`.
- **Why:** the current `jsdom` 30 requires Node `^24.15.0` while the pinned toolchain (`.nvmrc` 24, local 24.12.0) is older, and `happy-dom` is faster and has no engine constraint. Real-browser behaviour is covered by Playwright end-to-end tests later. Explicit `cleanup()` keeps test globals off.

## D-013 TypeScript 6.0 instead of 7.0

- **Chosen:** `typescript` 6.0.3 and `@types/node` 24.19.2.
- **Alternatives:** `typescript` 7.0.2 (latest on npm); `@types/node` 26.6.5 (latest on npm).
- **Why:** `typescript-eslint` 8.72.0, the latest release, supports TypeScript `>=4.8.4 <6.1.0`, so type-checked linting does not work with TypeScript 7. `@types/node` follows the Node 24 runtime from `.nvmrc` and the `engines` field instead of the newest major. Revisit when `typescript-eslint` supports TypeScript 7.

## D-015 WXT extension package layout, TypeScript setup and dev runner

- **Chosen:** `apps/extension` (`@sitenote/extension`) is a WXT 0.21 project with the default layout: `entrypoints/` at the package root, `wxt.config.ts`, output in `.output/` (`.output/chrome-mv3` for the Chrome build). Auto-imports are disabled (`imports: false`), so every WXT API is imported explicitly from `wxt/utils/*` and the code does not rely on generated globals. `tsconfig.json` extends `["./.wxt/tsconfig.json", "@sitenote/tsconfig/react.json"]`, in that order so the shared strict options win over WXT's, and its `include` lists `.wxt/wxt.d.ts`, `entrypoints` and `wxt.config.ts`. `.wxt/` is generated and gitignored, so the package has `"postinstall": "wxt prepare"`: `pnpm install` on a clean clone or in CI generates it before any `typecheck`. The manifest is built from `wxt.config.ts` (`name: "Sitenote"`, a one-line description) and takes `version` from `package.json`. No background script and no popup exist yet because phase 0 needs neither; WXT adds its dev-only background itself. There is no `test` script because the package has no unit tests; the extension is covered by Playwright end-to-end tests later. Dev runner: `webExt.disabled: true`, so `pnpm dev` builds and rebuilds into `.output/chrome-mv3` but never launches a browser. Load unpacked: open `chrome://extensions` (or `opera://extensions` in Opera GX), enable developer mode, choose "Load unpacked" and select `apps/extension/.output/chrome-mv3`. While `pnpm dev` runs, the dev build in that folder reloads on change; after a production `pnpm --filter @sitenote/extension build`, reload the extension manually.
- **Alternatives:** WXT auto-imports; a single `extends: "./.wxt/tsconfig.json"` with the shared options copied in; `prepare` instead of `postinstall`; letting WXT open Chrome or Firefox through `web-ext`; `@wxt-dev/module-react` and `@vitejs/plugin-react`.
- **Why:** explicit imports keep ESLint and `tsc` independent of generated globals. Extending both configs avoids duplicating the strict flags; WXT's own file only adds the `@`/`~` path aliases and `lib`/`module` defaults, and the shared config overrides the rest. `postinstall` is WXT's documented hook, pnpm runs it for workspace projects, and `wxt prepare` needs no browser. The owner uses Opera GX, which `web-ext` cannot launch. `@wxt-dev/module-react` only adds the React Vite plugin for fast refresh and auto-imports; Vite 8 already compiles JSX with the automatic runtime (see D-012) and a content script does not use fast refresh.

## D-016 Content script mounts the UI in a Shadow DOM root

- **Chosen:** `entrypoints/content/index.tsx` calls `createShadowRootUi` with `name: SITENOTE_ROOT_TAG` (from `@sitenote/core`), `position: "inline"` and `anchor: "body"`, and the content script sets `cssInjectionMode: "ui"` and `runAt: "document_idle"`. `onMount` creates a React 19 `createRoot` on the UI container and renders `HelloOverlay` from `@sitenote/ui`; `onRemove` unmounts that root. The CSS is imported from `entrypoints/content/style.css`, built into `content-scripts/content.css` and fetched by WXT into the shadow root; `content.css` is listed in `web_accessible_resources` for the same match patterns. The shadow root is `open` (the WXT default), so Playwright can pierce it.
- **Alternatives:** `position: "overlay"` or `"modal"`; `cssInjectionMode: "manifest"` or `"manual"`; an `iframe` UI; `createIntegratedUi`; a closed shadow root.
- **Why:** `HelloOverlay` positions itself with `fixed`, so the host element must not add layout: `inline` leaves the host as an empty inline element, `overlay` adds a zero-size relatively positioned block, and `modal` adds a full-viewport fixed layer that would swallow page clicks. `"manifest"` injection would put the Tailwind CSS, including preflight, into the host page. WXT's docs warn that the container may be `body`; in the installed `@webext-core/isolated-element` 3.0.0 it is a `div`, so `createRoot` is safe. Page styles cannot reach the overlay and its styles cannot reach the page; WXT resets inherited properties with `:host { all: initial !important }`.

## D-017 Tailwind 4 inside the shadow root

- **Chosen:** `style.css` is `@import "tailwindcss";` plus `@source "../../../../packages/ui/src";` and an `@source not` for `*.test.tsx` there. Tailwind 4.3.3 runs through `@tailwindcss/vite`. Three Shadow DOM pitfalls, each checked in the built CSS and in Chromium:
  - Theme variables: Tailwind 4 emits them on `:root, :host`, so they apply in the shadow tree without changes; WXT also rewrites `:root` to `:host` in the injected CSS.
  - `@property`: rules inside a shadow stylesheet are ignored, which leaves `--tw-shadow`, `--tw-ring-*`, `--tw-inset-*` and similar unregistered and makes `box-shadow` compute to `none`. WXT 0.21 already moves every `@property` and `@font-face` block out of the shadow CSS into a `<style wxt-shadow-root-document-styles>` element in the document head, removed again on unmount. Registered custom properties apply across shadow trees, so the initial values and `inherits: false` stay correct. Measured in Chromium: with that element the overlay has the full `shadow-lg`; with it removed `box-shadow` computes to `none`.
  - `rem`: the host page controls the `html` font size, which WXT's `all: initial` reset does not touch. `postcss-rem-to-responsive-pixel` (`rootValue: 16`, `propList: ["*"]`, `transformUnit: "px"`) runs in Vite's PostCSS stage after Tailwind generates the CSS, so theme variables become pixels (`--spacing: 4px`, `--text-sm: 14px`, `--radius-lg: 8px`) and every utility derives from them. Measured on a page with `html { font-size: 10px }` and on a default page: identical 14px text, 16px offsets and `12px 16px` padding.
- **Alternatives:** declaring the `--tw-*` initial values on `:host` (rejected: unregistered custom properties inherit, so a parent with `shadow-*` would leak `--tw-shadow` into a nested `ring-*` child; the only safe form is `*, ::before, ::after, ::backdrop`, which is Tailwind's own `@supports`-gated fallback and does not apply in Chromium); registering `@property` from our own code (duplicates WXT); leaving `rem` alone and trusting the host's font size; overriding the whole theme in `px` by hand; a hand-written PostCSS plugin instead of the package; `@import "tailwindcss" source(none)`.
- **Why:** reusing WXT's document-level registration is the smallest correct fix and is covered by the runtime measurement. The cost is that while the overlay is mounted the host page also gets `@property` registrations for names starting with `--tw-`; a host page that uses Tailwind 4 declares identical ones, and nothing else uses these names. `px` makes the overlay's size independent of arbitrary host `html` font sizes, which matters on the customer sites this tool targets; the trade-off is that the overlay ignores the user's browser default font size. Automatic source detection stays on so future extension components are picked up; it also generates one stray utility (`inline`, from the string `"inline"` in `index.tsx`), which is harmless.

## D-018 Phase 0 content script match patterns

- **Chosen:** `matches: ["http://localhost/*", "http://127.0.0.1/*"]`, no `<all_urls>`, no `permissions`, no `host_permissions`. A match pattern host without a port matches every port (Chrome match patterns documentation: the port is optional and acts as a wildcard unless given explicitly). Verified in Chromium with a server on a random port, on both `127.0.0.1` and `localhost`, while `127.0.0.2` did not match.
- **Alternatives:** `<all_urls>` or `https://*/*` now; `optional_host_permissions` with programmatic injection now.
- **Why:** phase 0 only needs the fixture site and the demo on a local dev server. This is temporary: phase 3 moves to optional host permissions requested per site, so the extension does not ask for access to every site at install time.

## D-019 Next.js web app: bundler, workspace packages and TypeScript

- **Chosen:** `apps/web` (`@sitenote/web`) is Next.js 16.4.2 with the App Router and `src/app/`, on Next's default bundler (Turbopack for both `next dev` and `next build`). `next.config.ts` sets `reactStrictMode: true` and `transpilePackages: ["@sitenote/core", "@sitenote/ui"]`, which is what makes the source-only workspace packages (D-010) compile; verified by importing both from a throwaway page in `next dev` and `next build` (`HelloOverlay` rendered with the `SITENOTE_ROOT_TAG` constant, and its Tailwind classes were present in the built CSS). `tsconfig.json` extends `@sitenote/tsconfig/react.json` and adds `allowJs: false`, `incremental`, `jsx: react-jsx` and the `next` plugin; `include` has `next-env.d.ts`, `next.config.ts`, `postcss.config.mjs`, `src`, `.next/types` and `.next/dev/types`. This is the shape Next 16 expects: `next build` did not rewrite the file. `next-env.d.ts` and `.next` are gitignored, so `typecheck` is `next typegen && tsc --noEmit -p tsconfig.json`: `next typegen` generates `next-env.d.ts` and the route types without building. `dev` and `start` pin port 3000. `apps/web/turbo.json` makes the web `build` depend on the web `typecheck` (`$TURBO_EXTENDS$` keeps the root `build` settings): both write to `.next` and `next-env.d.ts`, and running them in parallel could delete the generated types while `tsc` reads them. The page is a static placeholder landing; `@sitenote/core` and `@sitenote/ui` are already dependencies so later phases import them without touching the config.
- **Alternatives:** `next dev --webpack` and `next build --webpack`; compiled workspace packages; `experimental.externalDir`; an `@/*` path alias; `next lint` with `eslint-config-next`.
- **Why:** Turbopack is the default in Next 16 and handled the source packages without options, so there is nothing bundler-specific to maintain. `transpilePackages` is the supported way to consume TypeScript source from a monorepo package. A committed tsconfig that already matches Next's expectations avoids a dirty working tree after every build. `typegen` before `tsc` is Next's way to typecheck without a build. No path alias is configured because nothing needs one yet.

## D-020 Web styling: Tailwind 4 through PostCSS, system fonts

- **Chosen:** Tailwind 4.3.3 through `@tailwindcss/postcss` in `postcss.config.mjs` (Next's documented path). `src/app/globals.css` is `@import "tailwindcss";` plus the same `@source` and `@source not` pair as the extension for `packages/ui/src`, excluding `*.test.tsx`. There is no rem-to-px conversion: the web app owns its document and its `html` font size. The layout uses Tailwind's default `font-sans` system stack and no `next/font`.
- **Alternatives:** `@tailwindcss/vite` (Next is not Vite); `next/font/google`; `next/font/local` with a committed font file.
- **Why:** `next/font/google` downloads the font at build time, which makes CI builds depend on the network and on Google; the system stack keeps `next build` offline-safe and has no layout shift. A bundled font can be added later with `next/font/local` if the design needs one.

## D-021 `@next/eslint-plugin-next` with ESLint 10 flat config

- **Chosen:** `@next/eslint-plugin-next` 16.4.2 is a root devDependency and the root `eslint.config.js` applies its `core-web-vitals` flat config to `apps/web/**/*.{ts,tsx,js,mjs}` only, with `@next/next/no-html-link-for-pages` switched off.
- **Alternatives:** `eslint-config-next`; no Next rules; a per-package ESLint config in `apps/web`.
- **Why:** the plugin declares no peer on ESLint, loads under ESLint 10.13.0 and reports violations (checked with a throwaway file: `<img>` is flagged by `@next/next/no-img-element`). `no-html-link-for-pages` looks for a `pages/` directory, prints a warning on every run when there is none, and does not apply to the App Router. `eslint-config-next` would bring its own parser, React and import plugins that duplicate the root setup (D-011).

## D-022 WXT dev server on port 3100

- **Chosen:** `wxt.config.ts` sets `dev.server.port: 3100` with `strictPort: true`.
- **Alternatives:** WXT's default (first free port from 3000); moving the Next.js dev server to another port.
- **Why:** with both apps under `pnpm dev`, WXT's default picked 3000 because Next listens on the wildcard address while WXT binds `localhost`; on this machine `localhost` then resolved to WXT over IPv6 (`::1`) and returned 404 while `127.0.0.1` reached Next. A fixed port for WXT removes the race, and `strictPort` makes any future clash fail loudly instead of silently moving.

## D-023 Supabase CLI as a root devDependency and local config

- **Chosen:** `supabase` 2.121.0 as a root devDependency, run through `pnpm exec supabase`. Root scripts: `db:start` (`supabase start`), `db:stop`, `db:reset` (`supabase db reset`) and `db:status`. This release has no install script: the binaries come from platform `@supabase/cli-*` optional dependencies, so nothing is added to `allowBuilds` and installs work with `strictDepBuilds`. `supabase init` created `supabase/config.toml`; changes from the generated file: `project_id = "sitenote"` (the default was the directory name `Sitenote`), `[auth] site_url = "http://localhost:3000"`, `additional_redirect_urls = ["http://localhost:3000/**"]` and `enable_anonymous_sign_ins = true`, because guests join through Supabase anonymous auth (design section 6). Google OAuth is not configured; that is a manual step in phase 2. `[analytics] enabled = false`: on Docker Desktop for Windows the `vector` log collector needs the Docker daemon exposed over TCP and otherwise restarts in a loop, and analytics only powers the log explorer in Studio. Every other setting, including the edge runtime, stays at the generated default. The first migration is `supabase/migrations/20261020181430_init.sql` from `supabase migration new init`, kept as the empty file the CLI creates (timestamps are UTC `YYYYMMDDHHMMSS`; later migrations use `supabase migration new <name>`).
- **Alternatives:** a globally installed Supabase CLI or Scoop; `npx supabase`; a no-op SQL statement in the first migration; `site_url` on `127.0.0.1`.
- **Why:** a pinned devDependency gives every contributor and CI the same CLI version with no global install. `localhost` matches the URL the Next.js dev server prints and the owner opens, and cookie and redirect origins must agree. Anonymous sign-ins are off by default and the guest flow cannot work without them. An empty file is what the CLI itself generates. Verified with Docker Desktop on Windows: `pnpm db:start` brings up all services healthy, applies `20261020181430_init.sql`, and `pnpm db:reset` reapplies it cleanly. The CLI warns that `supabase/seed.sql` does not exist; the seed arrives in phase 2.

## D-024 End-to-end package and fixture site

- **Chosen:** a root workspace package `e2e/` (`@sitenote/e2e`) with `@playwright/test` 1.64.1, one project `chromium-extension`, `testDir: tests`, `retries: 2` and `forbidOnly` on CI, `list` reporter locally and `github` + `html` on CI, `trace: retain-on-failure`. The fixture site is static HTML and CSS in `e2e/fixtures/site/` (header, hero with a button, cards, an image placeholder, footer; no network resources), served by `e2e/fixtures/server.ts`, a dependency-free Node `http` server on `http://127.0.0.1:4173` that rejects paths resolving outside the site root, returns 404 and 405 correctly and sends `no-store`. Playwright's `webServer` runs it as `node fixtures/server.ts`: Node 24 strips TypeScript types by default, so no loader or build is needed. `@sitenote/e2e` depends on `@sitenote/extension` and has only an `e2e` script (no `build`, no `test`), so `pnpm e2e` builds the extension through Turborepo's `^build` and `pnpm test`/`pnpm build` never start Playwright. The Turborepo `e2e` task passes `CI` and `PLAYWRIGHT_*` through strict env mode.
- **Alternatives:** Playwright config inside `apps/extension`; `serve`, `http-server` or Vite preview as the fixture server; a separate fixture app package.
- **Why:** later phases add end-to-end tests that cover the extension, the web app, the demo and the guest flow together, so the suite belongs to neither app. A 100-line server with no dependencies is easier to trust than another package, and fixed port and host keep the URLs in tests stable.

## D-025 Loading the extension in Playwright

- **Chosen:** `e2e/fixtures/extension.ts` overrides Playwright's `context` fixture with `chromium.launchPersistentContext("", { channel: "chromium", args: ["--disable-extensions-except=<path>", "--load-extension=<path>"] })`, where the path is `apps/extension/.output/chrome-mv3` resolved from the fixture file, and fails with a clear message when the build is missing. Headless works with the `chromium` channel (the new headless mode supports extensions), so CI needs no virtual display. No `extensionId` fixture yet: the extension has no service worker in phase 0. The WXT shadow root is open, so locators pierce it directly (`page.locator("sitenote-root").getByTestId("sitenote-hello")`). The negative test routes two origins with `context.route` and the same HTML: `http://localhost:9` (inside the match patterns, the control that proves the content script injects into routed pages) gets the overlay, `http://outside.test` does not. On the owner's machine `%LOCALAPPDATA%\ms-playwright` is a symlink to `D:\Cursor Cache\ms-playwright`; `playwright install` fails on the symlinked path with an empty error, so browsers there are installed once with `PLAYWRIGHT_BROWSERS_PATH` set to the real directory. Nothing in the repo sets that variable.

## D-028 Anchoring engine: creation, resolution order and thresholds

- **Chosen:** the engine lives in `packages/core/src/anchoring` (one folder per module) and is framework-free.
  - Page identity: `parsePageUrl` accepts only `http:` and `https:`; `site` is `URL.origin`, `page` is origin plus pathname with trailing slashes removed; query, hash and credentials are dropped; `index.html` is kept as it is.
  - Element anchor: `selectors.css` is the first unique selector among, in order, `#id` (stable ids only), `[data-testid]`, `[data-test]`, `[data-cy]`, up to three other `data-*` attributes with stable values, `[aria-label]`, `tag[role]`, `tag[name]`, one or two stable classes on the tag and the plain tag. If no candidate is unique in the document, the builder walks up to six ancestors and tries, for each, its own candidates joined to the element's candidates with a descendant combinator and then a chain of child steps where each step is the first candidate unique among its siblings or `tag:nth-of-type(n)`. If nothing is unique, `css` is the nth path. `nthPath` is always the full `tag:nth-of-type(n)` chain from `body`. Every value goes through `CSS.escape`, and `id`, `class` and attributes are read with `getAttribute`, not with element properties, so a form control named `id` or `classList` cannot clobber them. `offset` is the clamped, 4-decimal fraction of the click inside the rect (0.5 on a zero-size axis).
  - Fingerprint: lowercase tag, text, stable classes (sorted, unique), rounded size. Similarity is `0.55 * text + 0.2 * classes + 0.25 * size` with text = Sørensen–Dice on lowercase character bigrams (both empty is 1), classes = Jaccard (both empty is 1), size = mean of the min/max ratio of width and height (both zero is 1); a tag mismatch is 0.
  - Element resolution: `id`, `testId`, `css`, `nthPath` in order; a selector counts only if it matches exactly one element outside the Sitenote host and the similarity is at least `ACCEPT_THRESHOLD` 0.5 (`NTH_PATH_THRESHOLD` 0.7 for `nthPath`, which is positional and fragile). Otherwise a fingerprint search over all same-tag elements under `body` (at most `MAX_FINGERPRINT_CANDIDATES` 5000, host subtree excluded) must have a best score of at least `FINGERPRINT_THRESHOLD` 0.75 and lead the runner-up by `FINGERPRINT_MARGIN` 0.05, otherwise the anchor is orphaned. Malformed stored selectors are treated as no match.
  - Text model: the concatenated raw `data` of all text nodes under `body` found by a `TreeWalker` that rejects the subtrees of `script`, `style`, `noscript`, `template`, `textarea` and `sitenote-root`; offsets map to `(text node, offset)` in both directions by binary search, including range boundaries that sit on elements.
  - Text anchor: `exact` is the selection with surrounding whitespace trimmed, `prefix` and `suffix` are up to 32 characters of the document text around it, `position` is the offset pair in the `body` text model and `container` is the css selector of the nearest ancestor whose computed `display` does not start with `inline` and is not `contents` (`body` as the fallback, also for documents without a browsing context).
  - Text resolution: (1) the container, if it matches exactly one element; every occurrence of `exact` inside it is scored by the length of the common suffix of the stored prefix plus the common prefix of the stored suffix, divided by the stored context length (1 when the context is empty), and the best occurrence is taken if it is unique and scores at least `CONTAINER_MIN_CONTEXT_SCORE` 0.5; (2) the same over the whole `body`, taking the best occurrence if it is strictly better than the others; (3) the stored `position`, if the text there equals `exact`; (4) the occurrence nearest to `position.start` among the best-scoring ones, with confidence multiplied by `TIE_CONFIDENCE_FACTOR` 0.5; (5) orphan. Confidence is `0.5 + 0.5 * context score`.
- **Refinements to design section 4 (the design only says "above a threshold"):**
  - A structural hit (`css`, `nthPath`) is rejected when both the stored and the current fingerprint have text and their text similarity is below `MIN_TEXT_SIMILARITY` 0.5. `id` and `testId` are not gated. Without the gate, two siblings with the same classes and size already score `0.2 + 0.25 + 0.55 * text`, which passes 0.5 for almost any English text, so after the cards of a grid are reordered `nth-of-type` would pin the comment to a different card instead of following the content.
  - The fingerprint text is read with the text-model walker (collapsed whitespace, 120 characters, early exit) instead of raw `textContent`, so inline scripts, styles, textareas and the Sitenote host never contribute to it.
  - A lone occurrence inside the container is trusted only with a context score of at least 0.5; otherwise the search continues over the whole document. Without this floor, a container selector that now points at a different block containing the same sentence (duplicated text, reordered sections) would win over the occurrence whose surroundings actually match.
  - The nearest-to-position tie-break considers only the best-scoring occurrences.
  - `exact` is trimmed, so a double-click selection with a trailing space anchors the same text as one without it.
- **Known limits:** the text model uses raw DOM text, so a page that changes only whitespace around the quote loses context score but still resolves when the quote itself is intact, and a quote whose own whitespace changed is orphaned; text in open shadow roots of the page is not part of the model; a pin on an element whose whole text was rewritten and which has no stable id or test id is orphaned.
- **Alternatives:** XPath or serialized Range anchors; the W3C text quote selector libraries (`dom-anchor-text-quote`, Hypothesis client) and `diff-match-patch` fuzzy search for text; accepting any unique selector match without a fingerprint check; a single weighted score for selectors and fingerprint search.
- **Why:** it follows design section 4 with the same data shape, so anchors stay small jsonb. Selector hits are cheap and strong evidence, so they get the lower threshold, but they need a content check because structural selectors silently point at a neighbour after a reorder or a removal. Fingerprint search is expensive and weaker, hence the higher threshold and the margin that turns ambiguous matches into orphans, which the sidebar shows instead of a wrong pin. Exact quote plus prefix and suffix is the W3C model and keeps the text path free of fuzzy matching, which would produce wrong highlights.

## D-029 Generated class names, ids and attribute values

- **Chosen:** `isStableClassName` rejects a class when it starts with `css-` or `svelte-` followed by a segment that contains a digit, or with `jsx-` followed by a digit, or when any segment of a token made only of `[A-Za-z0-9_-]` (split on `-` and `_`) is hash-like. A segment of at least five alphanumerics is hash-like when it mixes letters and digits and is not a number followed by letters (`100vh`, `2xl`) or letters followed by a number (`col12`, `html5`), or, when it has no digits, is at most eight letters long, has both cases and is not camel or Pascal case made of words that each contain a vowel (`navBar`, `YouTube` stay; `bdfBwQ`, `kbMcn`, `gsDKAQ` go). Every token with another character (`md:px-4`, `bg-[#fff]`, `w-1/2`, `!important`) is a utility class and is kept. This covers CSS Modules (`Button_root__a1B2c`, `_root_1x2y3_1`), Emotion, styled-components, styled-jsx and Svelte names. `isStableId` additionally rejects ids with `:`, `«` or `»` (React `useId`, Radix), the React 19.2 `_r_1_` form, digit runs of four or more, UUIDs, `ember123`, `ext-gen123`, `ext-comp-123`, `gwt-uid-123` and ids with a hash-like segment. `data-*` candidates skip state attributes (`data-state`, `data-open`, ...), boolean-like values, values longer than 64 characters or with hash-like words, and attribute names with a hash-like segment (Vue `data-v-7ba5bd90`).
- **Alternatives:** an entropy or n-gram score; a dictionary of English words; a fixed list of framework regular expressions only; keeping every class and relying on the fingerprint threshold.
- **Why:** hashed names change on every build, so a selector or fingerprint that contains them breaks on the next deploy, which is the main reason design section 4 skips them. A segment-level structural rule works without data files and without per-framework maintenance. Limits, accepted on purpose: a five-letter all-lowercase hash and a hash that happens to read as camel case with vowels are indistinguishable from words and are kept; the cost is one extra, weaker class in a selector candidate or fingerprint, and the selector still has to be unique and the fingerprint still has to agree.

## D-033 Database schema, deletion behaviour and integrity guards

- **Chosen:** nine tables in `public` (`profiles`, `workspaces`, `members`, `invites`, `sites`, `threads`, `comments`, `notifications`, `integrations`) and four enums (`member_role`, `thread_status`, `notification_kind`, `integration_provider`), created by `supabase/migrations/20261021090703_core_schema.sql`. Every table has `created_at`, `updated_at` and a `set_updated_at` trigger; `id` is `gen_random_uuid()` except `profiles.user_id`. Authored columns (`threads.created_by`, `threads.resolved_by`, `comments.author_id`, `invites.created_by`) are nullable with `on delete set null`, so removing a user (for example a periodic cleanup of anonymous guests) never deletes other people's conversations; everything owned by a workspace cascades with the workspace; `workspaces.owner_id` cascades because a workspace without an owner is unreachable. Integrity is enforced in the database, not only in policies: `threads.workspace_id` and `comments.workspace_id` are denormalised for RLS and Realtime filters and set (or, if supplied, verified) by `BEFORE INSERT` triggers from the site or thread; `threads.page_url` must equal the site origin or start with `origin/`; `threads.screenshot_path` must be `<workspace_id>/<thread id>.(png|jpg|jpeg|webp)`; anchors must be a JSON object with `kind` element or text (at most 32 KB), `context` and `integrations.settings` must be size-capped objects; `comments.mentions` may only contain workspace members and at most 50 ids; a `forbid_column_change` trigger makes the identity columns of every table (workspace, site, thread, author, owner, token, provider, user) immutable for every role including the service role, and lets only the `set null` of referential actions through; `members` has a partial unique index for one owner per workspace plus a trigger that only lets `workspaces.owner_id` hold the owner role and forbids granting or removing it; `sites.origin` is a bare lowercase http(s) origin and cannot change once threads exist; resolving a thread stamps `resolved_by` and `resolved_at` from `auth.uid()` and reopening clears them; editing a comment stamps `edited_at`; soft deleting stamps `deleted_at` on the server, blanks body and mentions, and makes the comment read-only. Invite tokens are 24 random bytes in hex from `pgcrypto`, because `base64url` is not available in `encode()` on PostgreSQL 17. `integrations.secret_id` is a plain uuid with no foreign key: the Vault secret lifecycle belongs to the Edge Functions that create it.
- **Alternatives:** `on delete cascade` for authored content; relying on policies alone for the denormalised columns and screenshot paths; a foreign key from `integrations.secret_id` to `vault.secrets`; a separate secrets table.
- **Why:** a `page_url` or screenshot path that a guest can point anywhere becomes a phishing link in the dashboard, or a way to make a service-role Edge Function attach another workspace's screenshot to the owner's ClickUp task, so these are constraints, not conventions. Triggers and constraints also protect against future bugs in code that runs with the service role and bypasses RLS.

## D-034 Access model: policies, column grants and deliberate deviations

- **Chosen:** RLS is enabled and forced on all nine tables. `anon` has no privilege on any table. `authenticated` gets column level privileges only: `INSERT` and `UPDATE` list the exact columns clients may write (for example `threads` insert has no `resolved_*`, `clickup_*` or timestamps, `threads` update is `status` only, `comments` update is `body`, `mentions` and `deleted_at`, `members` update is `role`), and `DELETE` exists only where the matrix allows it (`comments` has none). The policy matrix is implemented as designed, with these additions. A registered (non-anonymous) user may create workspaces, including a user who is a guest elsewhere, because "guest" is a role inside one workspace and the anonymous session is the real boundary. `workspaces` select also allows `owner_id = auth.uid()`, so `insert ... returning` works before the membership trigger is visible to the policy. The `threads` and `comments` insert policies re-check that the site or thread belongs to the stated workspace, so the policy stands without the trigger. `comments` update additionally requires current membership, so a removed member cannot keep editing. `notifications` select and update additionally require current membership of the workspace. `sites` update (owner) changes `origin` only and is blocked once threads exist. `profiles.email` and `integrations.secret_id` have no `SELECT` privilege for any client role, so a guest cannot harvest teammates' addresses and nobody can read, filter or sort by a vault reference. Consequence for client code: `select('*')` on `profiles` and `integrations` fails with `permission denied`; list the columns. Edge Functions use the secret key to read both.
- **Alternatives:** table level grants with policies only; exposing `profiles.email` to workspace members; a view for the safe columns; moving `email` out of `profiles`.
- **Why:** column grants close "set `created_by` to someone else", "move a thread to another workspace" and "make myself owner" at the privilege layer before any policy runs, and the triggers of D-033 close the same holes for the service role. Hiding the e-mail keeps the design's `profiles.email` column while limiting client-visible profile data to name and avatar. An owner who needs member e-mails later should get a dedicated `security definer` function, not a wider grant.

## D-035 Helper functions live in a private schema

- **Chosen:** `private.workspace_role`, `private.is_workspace_member`, `private.shares_workspace`, `private.is_anonymous` and `private.screenshot_workspace` are `security definer`, `stable` or `immutable`, with `set search_path = ''` and fully qualified names; policies wrap `auth.uid()` as `(select auth.uid())`. Every function in `private` has `execute` revoked from `public`; only these five are granted to `authenticated`, and neither `authenticated` nor `anon` has `USAGE` on the schema (policy expressions are resolved to function ids, so they still run, and a client cannot name `private.*` in any statement). PostgREST exposes only `public` and `graphql_public`, so none of this is reachable over HTTP. Trigger functions that call another `private` function are `security definer` for the same reason. `public` defines no function.
- **Alternatives:** helpers in `public` (exposed as RPC); granting `USAGE` on `private`; `security invoker` helpers reading `members` through its own RLS (infinite recursion).
- **Why:** a `security definer` function in an exposed schema is callable by any client, and helpers that read `members` through RLS recurse. The tests assert the exact execute and schema privileges and the pinned `search_path` of every function.

## D-036 Screenshots bucket

## D-044 Session cookies, `proxy.ts` and server-side identity

- **Chosen:** `@supabase/ssr` 0.12.7 with `Database` from `@sitenote/db`. Next 16 renamed `middleware.ts` to `proxy.ts` (checked in the bundled Next docs; `proxy` is a named export next to `config.matcher`): `src/proxy.ts` calls `refreshSession` from `src/supabase-proxy`, which builds a server client over the request cookies, calls `auth.getClaims()` so an expiring token is refreshed before the page renders, and writes the new cookies (and the no-cache headers `@supabase/ssr` hands to `setAll`) onto the response. The matcher skips `_next/static`, `_next/image`, `favicon.ico` and common static file extensions. Server components, actions and route handlers create a client per call with `createSupabaseServerClient()` (cookie store from `cookies()`; the `setAll` used in a server component swallows the write because Next forbids it there and the proxy has already refreshed), and read the identity with `getAuthenticatedUser()`, which wraps `auth.getClaims()` and returns `{ id, email, isAnonymous }` or `null`. `getSession()` is never used on the server. `getClaims()` verifies the JWT (locally against the JWKS with asymmetric signing keys; with the symmetric key of the local stack it asks the Auth server like `getUser()`), the `@supabase/ssr` type documentation prefers it over `getSession()`, and it carries `is_anonymous` and `email`, so a page needs no extra round trip to know whether the visitor is a guest. Data access still goes through the user's JWT, so RLS stays the authorization. The browser client (`createBrowserClient`) is a lazily created singleton, so `next build` works without Supabase variables; `env/` validates the three public variables with `zod/mini` the first time they are read and reports only the variable names. A proxy that fails (for example because the variables are missing) fails every request loudly instead of silently serving anonymous pages.
- **Alternatives:** `getUser()` on every request; `getSession()`; no proxy and refresh in pages; a client component that reads the session from `localStorage`.
- **Why:** server components cannot write cookies, so without the proxy an expired token is refreshed on every request and the new refresh token is lost, which then trips reuse detection. A single `getClaims()` path keeps the identity check in one place.

## D-045 Redirect targets after sign-in

- **Chosen:** every `next` value passes through `safeRedirectPath` (`src/safe-redirect`, default `/app`). It accepts a string of at most 2048 characters that starts with exactly one `/`, contains no backslash, no C0 or C1 control character and no Unicode line or paragraph separator, stays relative after up to three rounds of percent-decoding (so `/%2F...`, `/%5C...`, `%2F%2F...` and double encodings are rejected, while a malformed escape such as a lone `%` simply stops decoding), and resolves against a placeholder origin to the same origin. The returned value is the normalised `pathname + search + hash`, so `/a/..//evil`, which collapses to `//evil`, is rejected. The same function guards the sign-in page, the OAuth `redirectTo` and `/auth/callback`. Errors from the callback travel as one of three fixed keys (`missing_code`, `exchange_failed`, `access_denied`) and the sign-in page maps a key to a fixed message; unknown keys are ignored, so neither a provider's `error_description` nor a raw Supabase message is ever rendered. `/auth/sign-out` accepts `POST` only (a plain `<form method="post">`, no client JavaScript), clears the local session and answers `303` to `/`.
- **Alternatives:** an allow-list of paths; a regular expression only; `URL` parsing only; rendering provider error messages.
- **Why:** open redirects after login are the usual phishing vector, and browsers disagree on `/\` and on tabs inside `//`. Checking the raw string, the decoded forms and the parsed result catches each class independently. The unit suite lists every bypass found while designing it and the end-to-end suite repeats the main ones through the real sign-in.

## D-046 Sign-in form behaviour

## D-052 Service worker lifecycle and the refresh alarm

- **Chosen:** MV3 workers stop after about 30 seconds without events, which also stops the timers inside supabase-js. Therefore (1) every wake path ends in `getSession()`, which refreshes an access token that is inside the 90-second expiry margin of supabase-js: `runtime.onStartup`, `runtime.onInstalled`, the alarm and every valid incoming message; (2) subscribing to `onAuthStateChange` makes supabase-js emit `INITIAL_SESSION` on every boot, which schedules the alarm even when the worker was woken for another reason; (3) the `chrome.alarms` alarm `sitenote-auth-refresh` is a one-shot at `expires_at - 60 s`, re-planned by `planRefresh` after every session event and every wake (cleared on sign-out). The 60 s margin sits inside the 90 s that `getSession()` treats as "expired", so the alarm always triggers a real refresh; with the default one-hour token the alarm fires once an hour. When a refresh fails because the server cannot be reached the next attempt is 60 s later, which is also the floor for any plan (it matches the 60 s cooldown supabase-js applies after a failed refresh and stays above the 30 s granularity of Chrome alarms). A closed browser misses nothing, because `onStartup` runs the same refresh and nothing depends on an overdue alarm firing. Auth events are handled in a `setTimeout(0)` after the callback returns, because supabase-js documents that awaiting its own methods inside the callback can deadlock. The state broadcast covers `SIGNED_IN`, `SIGNED_OUT` and `USER_UPDATED`; token refreshes only re-plan the alarm.
- **Alternatives:** a periodic alarm every minute (about sixty wake-ups an hour for one refresh); a long-lived port or offscreen document to keep the worker alive; relying on the ticker inside supabase-js.
- **Why:** the single planned wake-up costs one worker start per hour, and the on-wake refresh makes the plan only an optimisation rather than a correctness requirement. The end-to-end suite proves both halves: it checks the stored alarm time against the stored `expires_at`, and it forces `expires_at` into the past, stops the worker and sees the next popup open get a new access token.

## D-053 Message protocol between the popup and the background

- **Chosen:** `src/messages` holds the `zod/mini` schemas, the single source for both sides. Requests: `auth.getState`, `auth.sendCode { email }`, `auth.verifyCode { email, code }`, `auth.signInWithGoogle`, `auth.signOut`; the e-mail is trimmed and limited to 254 characters, the code must be exactly six digits. A response is `{ ok: true, data }` or `{ ok: false, error: { code, message } }` where `code` is one of a fixed list (`invalid_request`, `forbidden_sender`, `unavailable`, `state_failed`, `invalid_email`, `rate_limited`, `send_failed`, `invalid_code`, `verify_failed`, `google_disabled`, `google_cancelled`, `google_failed`, `sign_out_failed`) and `message` comes from one constant map, so a raw Supabase message never crosses the boundary; the UI renders the message of the code, not a string from the wire. The single `runtime.onMessage` listener calls `createMessageRouter`, which answers `forbidden_sender` unless `sender.id === browser.runtime.id`, `invalid_request` for anything that does not parse, runs the wake-up refresh and dispatches with an exhaustive `switch`; the listener returns `true` and answers asynchronously. `src/message-client` is the UI side: `sendMessage` validates the response with the schema of the request type and turns a missing background, a rejected promise or a malformed answer into `unavailable`; `onAuthStateChanged` listens for the `auth.stateChanged` broadcast, checks the sender and the schema, and returns the unsubscribe function. The background broadcasts with `runtime.sendMessage`; a rejection because no page is open is expected and ignored.
- **Alternatives:** `chrome.runtime.connect` ports; one untyped `{ type, payload }` shape; returning Supabase errors as they are.
- **Why:** content scripts and, later, web pages through `externally_connectable` are less trusted than the service worker, so every message is parsed rather than cast, and fixed codes keep error text out of attacker-controlled channels.

Every async callback (`onSubmit`, `onEditComment`, `onDeleteComment`) is typed `(…) => Promise<void>`, so the UI can tell success from failure and keep the user's text on failure. `PinLayer` accepts an optional `pending` flag per pin and an `activeThreadId`, and `ThreadPanel` takes `thread: ThreadView | null` (`null` is the new-thread mode, where `onSubmit` creates the thread and `onClose` cancels it). Comment bodies, author names, anchor labels and toast messages are rendered as text only; bodies keep line breaks with `whitespace-pre-wrap` and are not auto-linked. Avatar URLs are accepted only as `https:` (anything else falls back to the initial) and are loaded with `referrerpolicy="no-referrer"`. The orphan state is a flag on the thread: orphaned threads, open or resolved, appear only in the "Orphaned" group, and the header counts partition the list (open, resolved, orphaned) so that nothing is counted twice.
- **Alternatives:** a React context for panel and toast state; letting each component call a repository interface; synchronous callbacks plus an `error` prop for every operation; a single `ThreadPanel` and a separate `NewThreadPanel`; a shared `HoverCard` base; auto-linking URLs in bodies.
- **Why:** props and callbacks keep the package portable between the content script and the web demo and make every state reachable in a plain component test. Promise-returning callbacks are the smallest contract that supports "keep the text, show the error". One component with a `null` thread avoids duplicating the header, positioning and focus logic. Auto-linking is deferred because it needs a link policy (scheme allow-list, `rel`, tracking parameters) that belongs to a later phase.

## D-059 Positioning: fixed viewport coordinates and pure placement functions

- **Chosen:** every floating element is `position: fixed` and placed with viewport pixels (`getBoundingClientRect` space), so the content script does the page-to-viewport conversion once and the components never read page scroll. `Pin` is 24 px, centred on its `x`,`y` (the click point). `PinLayer` is `fixed inset-0` with `pointer-events: none` and each pin re-enables `pointer-events: auto`, so the layer never swallows page clicks. `placePanel(anchorRect, panelSize, viewport)` returns `{ left, top, side }`: right of the anchor if the panel fits, otherwise left, otherwise centred below, otherwise centred above, and as a last resort clamped inside the viewport; every result keeps an 8 px margin and an 8 px gap to the anchor, and the vertical position of side placements is clamped. `placeAbove` centres a smaller element above a rectangle, flips below when there is no room and clamps horizontally; `SelectionButton` uses it with a fixed 96 x 32 size. `ThreadPanel` is 320 px wide, measures its own height with a `ResizeObserver` (the first callback runs before paint) and tracks the window size through `useViewport`; its `max-height` is the viewport height minus both margins, and the comment list scrolls inside it. Stacking is defined once in `src/z-index` (`Z_INDEX`: highlight, pins, selection button, sidebar, panel, banner, toast, strictly ascending and below 2147483647) and applied through inline `style` because the values are not Tailwind steps. `SelectionButton` prevents `mousedown` default so that clicking it does not collapse the text selection it is about to anchor.
- **Alternatives:** `position: absolute` in page coordinates; CSS anchor positioning; Floating UI; CSS `transform` for pin centring; a z-index scale of small integers.
- **Why:** the design already renders pins in a fixed layer updated on scroll and resize, so viewport coordinates are the natural contract. A pure placement function is trivially table-testable; Floating UI would add a dependency for one flip rule and CSS anchor positioning is not available in the browsers the extension must support. Offsets instead of `transform` avoid a stacking and blur side effect on text. Large z-index values keep the overlay above host pages that use big numbers while leaving `2147483647` free for the phase 0 `HelloOverlay`.

## D-060 Focus, keyboard and accessibility choices

- **Chosen:** all controls are native `button`, `textarea`, `time`, `ul` elements with visible `focus-visible` outlines (2 px, `blue-700`). `ThreadPanel` is a non-modal `role="dialog"` named by its heading with no focus trap; on open focus goes to the composer, and on unmount focus returns to the element that was focused inside the same root before the panel mounted (found through `getRootNode().activeElement`, so it also works in a Shadow DOM), but only if focus is still inside the panel or nowhere, so a click on another pin keeps the focus it just got. `Escape` closes the panel from anywhere inside it and does not propagate to the page; inside an edit composer it cancels only the edit; inside the new-thread composer it cancels the thread. Delete is a two-step in-panel confirmation (`role="group"`, focus on the safe "Keep" button, an inline alert when the request fails), never `window.confirm`; after cancelling an edit or a delete, focus returns to the Edit or Delete button, and after a successful delete it moves to the comment so that `Escape` keeps working. `Pin` is a button with `aria-label="Thread N, open|resolved|pending"`, `aria-haspopup="dialog"` and `aria-expanded` for the active pin. `ToastRegion` is a polite `role="status"` live region that is always mounted; error toasts add a visually hidden "Error:" prefix instead of a nested `role="alert"`, never auto-dismiss, and info toasts pause their 5 s timer while hovered or focused. `CommentModeBanner` is a `role="status"` bar. `HighlightBox` and decorative glyphs are `aria-hidden`. Motion is limited to a `motion-safe:` hover scale on pins. Colours are Tailwind neutral, blue, red, emerald, purple, rose, amber and teal steps 600 to 900 on white or white text on them, all at least 4.5:1 (AA); the muted resolved pin uses `neutral-600` (7.8:1).
- **Alternatives:** a focus trap in the panel; `aria-modal` dialogs; `role="alert"` for every error; a `tabindex` roving pin list; native `<dialog>`.
- **Why:** the user keeps working on the page while a thread is open, so a trap or a modal would be wrong; returning focus to the pin keeps keyboard users oriented. Restoring focus conditionally avoids the focus-stealing race when the open panel is replaced by a click. Nested live regions are announced twice by several screen readers. Native `<dialog>` brings top-layer and backdrop behaviour that is not wanted here and is awkward inside a shadow root.

## D-061 Composer behaviour

- **Chosen:** a `form` around an autosizing `textarea` with `rows=2`. Submit is the button or `Ctrl`/`Cmd`+`Enter` (plain `Enter` adds a line; keystrokes during an IME composition are ignored); the text is trimmed, empty or whitespace-only text cannot be submitted, and `maxLength` 10 000 plus a guard in the submit path caps the length. A "n / 10000" counter replaces the shortcut hint from 9 000 characters on and turns red above the limit; it and the error message are linked through `aria-describedby`. While submitting (the `submitting` prop or an unresolved promise returned by `onSubmit`) the textarea is `readOnly` with `aria-busy` and the buttons are disabled; the textarea is not `disabled` because a disabled control drops keyboard focus and breaks `Escape` handling. On resolve the field is cleared; on reject the text is kept, the field is focused again and the `error` prop is shown (or a fixed fallback message when the parent passes none), cleared as soon as the user edits. Height is set from `scrollHeight` plus the border, capped at 176 px (8 lines of 20 px plus padding), after which the field scrolls. `autoFocus` is implemented with an effect (cursor at the end) instead of the React attribute so that the parent can read the previously focused element before focus moves. `Escape` calls `onCancel` and stops propagation only when `onCancel` is given.
- **Alternatives:** `field-sizing: content` (not in Firefox); `disabled` while submitting; clearing the field before the request finishes; a rich-text editor; mentions (the design lists them for a later phase).
- **Why:** these are exactly the failure paths users hit (offline, double submit, accidental `Escape`), and each is covered by a test. Clearing only after success follows the design rule that unsent comments stay in the composer.

## D-063 `create_thread` function

- **Chosen:** `public.create_thread(p_site_id, p_page_url, p_anchor, p_context, p_body, p_mentions) returns public.threads` in `20261021173937_create_thread.sql`: `plpgsql`, `security invoker`, `set search_path = ''`, executable by `authenticated` only (`revoke ... from public, anon` because Supabase's default privileges grant new functions to `anon`). It rejects a body without a non-space character (`\S`, the same test as the `comments_body_present` constraint) with `23514`, inserts the thread with `created_by = auth.uid()` and then the first comment with `author_id = auth.uid()`, and returns the thread row. Both inserts run as the caller, so the column grants, the RLS policies, the `workspace_id` triggers and every check constraint still decide; the function adds no privilege. A failure in the second insert (a mention of a non-member, a body over 10 000 characters) rolls the thread back, because the function body is one transaction. The design's extra check `jsonb_typeof(anchor) = 'object' and anchor ? 'kind'` already exists in `threads_anchor_valid` (object, `kind` is `element` or `text`, at most 32 KB), so no new constraint was added; clients still validate the full shape with `anchorSchema`. The only function in `public` is now this one, and the schema tests assert that it is a security invoker with a pinned search path and executable by `authenticated` only, replacing the old "no function in `public`" test. The RLS suite `create-thread.rls.test.ts` covers owner, member and guest (allowed), outsider, anonymous non-member and the unauthenticated role (denied), an empty or whitespace body, rollback after a failing first comment, a bad anchor, a foreign page URL and an unknown site, each with a check that no thread is left behind.
- **Alternatives:** inserting the thread and the comment in two client calls; a `security definer` function; a trigger that creates the first comment; a new anchor constraint.
- **Why:** one round trip and one transaction remove the "thread without a comment" state the design's flow cannot tolerate, and `security invoker` keeps RLS the only authorization (D-034, D-035) instead of a second place to get wrong.

## D-064 Message protocol: error codes, sender scopes and page binding

- **Chosen:** the 2c protocol (D-053) is extended, not duplicated. `messages` now holds the auth requests, the data requests and one `requestSchema`; `RESPONSE_SCHEMAS` has an entry for every request type, and `message-client.sendMessage` validates a response against the schema of its request. The error code list gains `unauthorized`, `forbidden`, `not_found`, `validation`, `network`, `unknown` and `page_unavailable`, each with a fixed message, so the generic names `ErrorCode`, `MessageResult`, `ErrorResponse` and `SuccessResponse` replaced the `Auth*` ones. Requests: `sites.forOrigin`, `threads.list`, `threads.create`, `threads.setStatus`, `comments.create`, `comments.update` (body only), `comments.delete`, `workspaces.list`, `sites.enable`, `sites.disable`. Inputs are validated at the boundary: bare http(s) origins, normalized page URLs (`parsePageUrl(url).page === url`), UUIDs, bodies trimmed to 1 to 10 000 characters, at most 50 mentions, JSON-only context and `anchorSchema` anchors. The router classifies the sender: an extension page (`sender.url` under the extension origin), a content script (`sender.id` is ours and `sender.tab` exists) or foreign (everything else, including our own id without a tab or an extension URL). Auth, `workspaces.list`, `sites.enable` and `sites.disable` are for extension pages only; `sites.forOrigin` is open to extension pages for any origin and to a content script for its own origin only; the thread and comment requests need a tab, a locally enabled origin for the sender's URL, and for `threads.list` and `threads.create` a `siteId` equal to the enabled site of that origin and a page URL on that origin. Everything else answers `forbidden_sender` or `forbidden`. Database errors map through `mapDataError` (`42501` and 403 to `forbidden`, `PGRST301` to `PGRST303` and 401 to `unauthorized`, `PGRST116` and 404 to `not_found`, classes 22 and 23 to `validation`, 429 to `rate_limited`, fetch failures to `network`, anything else to `unknown`); no database message crosses the boundary. The data layer answers `unauthorized` itself when there is no session, because RLS would otherwise return empty lists for an anonymous caller.
- **Alternatives:** a second message channel for page requests; trusting `sender.id` alone for content scripts; letting a content script ask for any site id; returning Supabase messages.
- **Why:** a content script runs in a page the extension does not control, so it gets the narrowest authority that still lets it work: its own origin's site and nothing administrative. RLS stays the real authorization, the binding only stops a stale or confused script from acting for another site. Updating a thread the policy hides answers `not_found`, not `forbidden`, because PostgREST returns zero rows for both cases and the two cannot be told apart without another query.

## D-065 Transport shapes and the data service

- **Chosen:** `transport` defines the zod shapes that cross the boundary: `SiteInfo` (`siteId`, `workspaceId`, `workspaceName`, `role` and `userId`, which the plan's shape did not list; the content script needs it to decide which comments the user can edit, because it may not call `auth.*`), `WorkspaceInfo`, `ThreadRecord` and `CommentRecord`, all with ISO strings for dates. `threads.list` is one query: the page's threads with their comments and the author profiles of both through the `threads_created_by_fkey` and `comments_author_id_fkey` embeds, ordered by creation time (comments sorted in the mapper). A thread whose stored anchor fails `anchorSchema` is returned with `anchor: null` for the UI to treat as orphaned instead of failing the list. An author whose profile is hidden (the member left, the profile policy needs a shared workspace) is shown as "Former member" and a deleted user as "Deleted user". `threads.create` calls `create_thread` (D-063) and then reads the thread back with the same select, so the caller gets exactly what a later `threads.list` returns; `comments.create`, `comments.update` and `comments.delete` return the comment. Deleting sets `deleted_at` and the database trigger blanks the body and mentions (D-033). `comments.create` first reads the thread's `workspace_id`, because the generated insert type requires the column even though the trigger fills it; the extra read also turns a missing thread into `not_found`. `sites.forOrigin` answers from the local enablement map plus two queries (the caller's membership with the workspace name, and the site row), and answers `null` when any of them is gone. Enabling a site inserts the origin only when it is not in the workspace yet; a unique violation from a race re-reads the row, and a guest's insert is refused by RLS and surfaces as `forbidden`.
- **Alternatives:** separate queries per thread; returning raw rows; a `security definer` function that returns the whole payload; adding `workspaceId` to `comments.create`.
- **Why:** one embedded query keeps a page load at one round trip, and mapping in the background keeps database column names, timestamp formats and null handling out of the content script and the UI.

## D-066 Realtime owned by the worker

- **Chosen:** the content script holds a `runtime.connect({ name: "sitenote:page" })` port and sends `page.subscribe` (`siteId`, `workspaceId`, `pageUrl`) and, after navigation, `page.update`. The hub (`src/realtime-hub`) validates every message and the sender (a content script of an enabled origin whose site and workspace match the local map, and a page URL on that origin), keeps one Realtime channel per site reference-counted by ports, and closes it with the last port. Each channel listens to `postgres_changes` on `threads` filtered by `site_id=eq.<id>` and on `comments` filtered by `workspace_id=eq.<id>`. A per-site index maps thread ids to page URLs and is filled from thread events; a comment event of an unknown thread looks its page up once (`findThreadPage`) and caches it. The hub forwards typed events to the ports on the matching page only: `threads.changed { threadId }` and `comments.changed { threadId }`. The events carry no row data: the client re-fetches the page through `threads.list`, coalescing bursts into at most one extra request (a payload cannot carry the joined author profiles, so applying payloads would need a second lookup anyway, and a refetch cannot drift). `page.subscribed` is sent when the channel reports `SUBSCRIBED` (immediately for a late joiner, and again after every rejoin), so a client that refetches on each acknowledgement cannot miss a change made before the subscription was live; without a session no channel is opened and the acknowledgement is immediate. `realtime.setAuth` is called with the new access token on every auth state change; signing out closes every channel and signing in reopens the ones that have ports. When the site is disabled the hub sends `site.disabled` and disconnects the ports, and the content script tears itself down. The content side (`page-connection`) reconnects after a disconnect with a delay that doubles from 500 ms to 30 s and resets on an acknowledgement, and `data-live` on the shadow host (a test attribute, like `data-thread-count` and `data-comment-count`) shows the state. A stopped worker (the end-to-end test stops it through CDP) disconnects the ports; the next `runtime.connect` wakes it, `onConnect` is registered synchronously at start, and the acknowledgement triggers the refetch. Known limit: Realtime does not deliver `DELETE` events that are filtered on a non-key column, so a thread deleted by an owner disappears from other open pages at their next fetch or navigation; the hub handles the event if it ever arrives. Threads are never deleted by the UI in this phase.
- **Alternatives:** a channel per tab in the content script (it would hold a token and a WebSocket in every page, against design section 6); a broadcast channel written by clients; applying row payloads in the client; acknowledging when the port connects.
- **Why:** one connection per site instead of per tab, tokens only in the worker, and no way to miss an event between "fetched" and "subscribed".

## D-067 Site enablement: optional host permissions and runtime registration

- **Chosen:** the static content script `matches` of phase 0 (D-018) and `host_permissions` are gone. The manifest has `optional_host_permissions: ["http://*/*", "https://*/*"]` and the permissions `storage`, `identity`, `alarms`, `scripting` and `activeTab` (the last one lets the popup read the URL of the tab it was opened on; it shows no install warning). The content script is declared with `registration: "runtime"` and no `matches`, so WXT builds `content-scripts/content.js` and adds nothing to the manifest (WXT would otherwise copy `matches` into `host_permissions`). Its CSS is imported with `?inline` and passed to `createShadowRootUi({ css })`, so no `web_accessible_resources` entry per origin is needed and the content script never fetches an extension URL from the page; `noScriptStartedPostMessage` stops WXT from posting a message to the page window. `sites.enable` runs in the worker: check that the popup obtained the permission (`permissions.contains`), find or insert the site row, `scripting.registerContentScripts` (id `sitenote:<origin>`, `matches: [<origin>/*]`, `runAt: document_idle`, `persistAcrossSessions: true`, replacing a registration of the same id), write `{ origin -> { siteId, workspaceId } }` to `chrome.storage.local` and only then `scripting.executeScript` into the popup's tab; if the injection fails the map entry and the registration are removed and the answer is `page_unavailable`. The entry has to exist before the injection because the injected script asks `sites.forOrigin` immediately (the first run of the end-to-end test failed on this order). `sites.disable` drops the entry first, unregisters, removes the permission (a failure there is ignored, for example for the required fixture hosts of the e2e build) and tells the connected tabs, which unmount. `reconcile()` runs at browser start and on `permissions.onRemoved`: every stored origin whose permission is gone is torn down without touching the permission. A second injection into a tab replaces the first, because the WXT content script context invalidates the older one through a document event (covered by an end-to-end test). The popup, not the worker, calls `permissions.request` (it needs the user gesture).
- **Alternatives:** `<all_urls>` host permissions; a static content script per known site; `activeTab` only; registering the script from the popup; inline injection of the CSS through `web_accessible_resources`.
- **Why:** design section 9 asks for optional host permissions per site. Match patterns with a port (`http://127.0.0.1:4173/*`) were checked end to end: they register, inject after a reload and unregister.

## D-068 The e2e build variant and the production manifest guard

- **Chosen:** `chrome.permissions.request` shows a native prompt that Playwright cannot click: a scratch extension with only optional host permissions kept the request pending for 15 s in headless Chromium, and with `host_permissions` for `127.0.0.1` and `localhost` the same request resolved `true` in 1 ms. So the end-to-end suite loads a second build, produced by `pnpm --filter @sitenote/extension build:e2e` (`wxt build --config wxt.e2e.config.ts`), which differs from production in exactly two things: `host_permissions` is `http://127.0.0.1/*` and `http://localhost/*` (a port-less pattern matches every port), and the output folder is `.output/chrome-mv3-e2e` (`outDirTemplate`). CI runs `pnpm check:manifest` (`scripts/assert-production-manifest.ts`) on the real `.output/chrome-mv3/manifest.json` after `pnpm build`; the script fails on any of those conditions (checked by pointing it at the e2e manifest). Deviations from the brief, both deliberate: a separate WXT config file instead of the environment flag `WXT_E2E=true` (setting an environment variable inside a package script is not portable to Windows, and `--mode e2e` was tried first: WXT derives `process.env.NODE_ENV` from the mode, so React shipped in development mode in that build, and the build that is tested must be the production bundle).

## D-072 Content script structure and data flow

- **Chosen:** the content script is a thin shell (`content-main`) around `src/content-controller`, which owns one `useSyncExternalStore`-based store (`src/store`, about 30 lines, no new state library) and every side effect. The store holds the site, the thread records of the current page, one resolution per thread (`resolved` with a live `Element` or `Range`, or `orphaned`), the measured pin positions, and the UI state (comment mode, hover box, active thread, pending thread, text selection, sidebar, toasts, the panel error). `content-app` is a pure React component that reads the store and calls the controller's actions; `view-model` maps records to `ThreadView`s (numbers by creation time, `canEdit` only for the user's own comments that are not deleted, the anchor label, the `orphaned` flag) and holds the status rule (owners and members change any thread, a guest only their own). Nothing was added to the data path: the controller builds the 3b `page-session` (same `sendMessage`, same Port) and applies its state; a thread array is taken from the session only when its identity changed, so local patches survive the session's own `live` updates. Mutations apply the returned record straight to the store (`comments.create`, `comments.update`, `comments.delete`, `threads.setStatus`, `threads.create`), so the panel updates without waiting for the Realtime refetch, which later replaces the array with the same data. Every small concern is a module with its tests: `anchor-target`, `pin-tracker`, `comment-picker`, `selection-watcher`, `dom-watcher`, `url-watcher`, `document-style`, `text-highlighter`, `event-isolation`. The UI is mounted in the shadow root of the 3b `createShadowRootUi`; `HelloOverlay` is deleted from `@sitenote/ui` (the "Sitenote is running" marker of D-070 is now the launcher) and `Launcher` (a pill with the number of open threads, `aria-expanded`, its own z-index layer) was added. The sidebar is keyed statically, not by thread id as the 3a note suggested: it holds no per-thread focus state, and a per-thread key would collapse its "Show resolved" list on every selection; the panel is keyed by thread id (`"pending"` for a new thread). Focus moves into the sidebar when it opens and back to the launcher when it closes. The test attributes on the host (`data-thread-count`, `data-comment-count`, `data-live`, `data-comment-mode`) stay and are only written when their value changes. Keyboard and pointer events (`keydown`, `keyup`, `keypress`, `mousedown`, `mouseup`, `click`, `dblclick`, `pointerdown`, `pointerup`, `contextmenu`) are stopped at the shadow root container so that typing in the composer does not trigger hot keys of the page and clicks in the panel do not close the page's own popovers.
- **Alternatives:** a state library; a React context; letting the components talk to the message client; patching nothing locally and waiting for Realtime; a second data path for the overlay.
- **Why:** one controller that is testable with a fake `send` and a fake connection keeps the DOM work out of React, and the content script bundle grew only from 286.00 kB to 333.33 kB (the anchoring engine and the thread UI), measured on the production build.

## D-073 Comment mode, picking and text selection

- **Chosen:** comment mode is state in the controller; the popup button and the worker's shortcut command reach it through the 3b `commentMode.toggle` message, the banner's Exit button and Escape leave it. While it is on, `src/comment-picker` listens on the document in the capture phase: `mousemove` (and `scroll`, `mouseleave`) update the hover box once per animation frame from `document.elementFromPoint`, ignoring `html`, `body` and anything inside the extension host; `click` is cancelled (`preventDefault` and `stopImmediatePropagation`) so the page does not react, and then picks the element under the pointer with `createElementAnchor`, unless the click came from the keyboard (`detail` 0) or text is selected (a drag selection ends in a click, and the selection button handles it). Clicks that start inside the extension UI are left alone. Placing a thread keeps comment mode on so several comments can be left in a row. Escape is a capture listener on the window: events whose target is inside the extension host are ignored (focus in the panel or sidebar, where Escape closes the panel first), otherwise it cancels a pending thread, else leaves comment mode, and only then calls `stopImmediatePropagation` so that a page that has nothing to do with Sitenote still sees its own Escape. The cursor is `crosshair` on `html` and every descendant (`!important`, with the extension host reset to `auto`), applied by a document-level style that exists only while the mode is on. Text selection works in every mode: `mouseup`, `keyup` and `selectionchange` on the document feed `selection-watcher`, which ignores collapsed or whitespace-only selections and selections that touch the extension host, keeps a cloned range, and `SelectionButton` appears above it; the button creates a text anchor with `createTextAnchor`, drops the page selection (the pending highlight takes over) and starts a pending thread at the end of the selection. A selection that cannot be anchored produces an info toast. The 3b note stands: the keyboard shortcut itself cannot be pressed by Playwright, so the end-to-end tests use the popup button, which sends the same message.
- **Alternatives:** a full-viewport transparent catcher over the page; leaving comment mode after each placed thread; cursor style in the shadow root; text selection only inside comment mode.
- **Why:** a catcher would break scrolling and hover on the page; cursor style has to be on the page's own document; keeping the mode on is what reviewers expect when they leave many comments.

## D-074 Pin tracking

- **Chosen:** `src/pin-tracker` measures targets (an element with the click offset, or a text range) and reports viewport positions to the store. It is event driven and scheduled once per `requestAnimationFrame`: scroll (capture, so scrolling containers count), resize, intersection changes and explicit invalidation (the DOM watcher) request a frame; the listeners and the `IntersectionObserver` exist only while there is at least one target. Each frame is one batch of reads and one write: only targets whose element (the element itself, or the common ancestor element of a range) intersects the viewport are measured, except forced targets (the open thread, the pending thread, the text selection), and a measurement is reported only when something changed. Element pins use `pinPosition(element, offset)`, text pins the right and top edge of the first client rectangle of the range; a pin is `visible` only inside the viewport and when the target has boxes. Resolved threads are tracked only while open in the panel, so their pins are hidden unless opened from the sidebar ("Show resolved" stays the sidebar's own list toggle, phase 4 owns the full status UX). A detached element or a collapsed range is skipped until the DOM watcher re-resolves it. Where `IntersectionObserver` is missing every target is measured.
- **Alternatives:** a permanent `requestAnimationFrame` loop; measuring every pin on every scroll event; a `ResizeObserver` per anchor.
- **Why:** nothing runs on a page that has no pins, scroll costs one frame of reads, and layout shifts that do not scroll are picked up by the DOM watcher's debounced invalidation. Known limit: a layout shift that touches no DOM node (for example an image that finishes loading) moves pins only on the next scroll, resize or DOM change.

## D-075 Highlights and the two document-level styles

- **Chosen:** text highlights use the CSS Custom Highlight API: `CSS.highlights.set("sitenote", new Highlight(...ranges))` for the ranges of open threads, the open thread and the pending thread, with `::highlight(sitenote)` (blue at 25% opacity) installed once by `src/document-style` as an adopted constructable stylesheet, which also works on pages with a strict `style-src` because it is CSSOM, not markup. The end-to-end test checks `CSS.highlights.has("sitenote")` and that the sheet is adopted in the page document. If adoption throws the same module falls back to a `<style>` element in `head`; if the Highlight API is missing the controller sets `fallbackHighlights` and the app draws one `HighlightBox` per client rectangle of the visible text targets. The only other document-level style is the comment mode cursor (D-073). Both are removed when the content script stops, so disabling a site leaves nothing behind.
- **Alternatives:** wrapping the text in `<mark>` elements; drawing boxes always; a `<style>` element only.
- **Why:** wrapping mutates the page and breaks its own scripts; boxes need layout reads for every range on every frame; the adopted sheet is the CSP-safe way.

## D-076 Re-resolution and single page app navigation

- **Chosen:** one rule decides what is resolved again, in `reconcileResolutions`: a resolution is kept while its target is alive (the element is connected, the range is not collapsed and both ends are connected); everything else (detached, collapsed, orphaned, new) is resolved with `resolveElementAnchor` or `resolveTextAnchor`, and the same map is returned when nothing changed so no render is triggered. It runs on every thread refetch and on every settled DOM change. `src/dom-watcher` observes `document.body` (subtree, child list, character data, attributes), drops records that touch the extension host (its attributes, its children, its own insertion), and calls back 250 ms after the last change, or at most 2 s after the first one so a page that animates attributes forever still settles. A settled change also invalidates the pin tracker and checks the URL. `src/url-watcher` reports a change of the normalized page URL (origin and path, no query or hash) from the Navigation API's `currententrychange` when it exists, from `popstate` and `hashchange`, and from the DOM watcher's check. On a page change the controller clears the threads, the resolutions, the panel and the selection at once, tells the Port the new page and reloads the threads; `page-session` now drops a list that was requested for a page the user has already left, so a slow answer cannot show old pins on the new page (a unit test fails without the guard). Orphans are retried on every settled change and every refetch, which is cheap for element anchors and one text model per orphaned text anchor; a page with very many orphaned text threads would pay for that on each settle. A thread deleted on another client disappears at the next fetch, as 3b noted.
- **Alternatives:** patching `history.pushState` in the page (needs the main world); WXT's polling `wxt:locationchange`; re-resolving every thread on every mutation.
- **Why:** the Navigation API covers `pushState` without touching the page's world, and the observer fallback catches routers on other browsers.

## D-077 Thread actions, failures and permissions in the panel

- **Chosen:** creating a thread is optimistic in the sense the UI needs: the pending pin and panel exist from the click, the request carries `context: {}` (phase 5 fills it), and on success the pending pin becomes the real thread (same target, no re-resolution) and the panel switches to it. On failure nothing was added, so there is nothing to roll back: the pending pin and the typed text stay (the composer's promise rejects), the panel shows the error text, and an error toast with Retry re-sends the same body; a second submission while one is in flight is refused, and a thread that was created for a page the user has meanwhile left is not added to the new page. Replies, edits and deletions apply the returned record on success and reject with the user-facing message on failure, which the composer and the comment item already turn into "text kept" and "could not delete". A status change that fails raises the same kind of retry toast. At most three toasts are kept. Who may resolve or reopen follows the RLS matrix: owners and members for any thread, guests for their own (`canChangeStatus`; the button is hidden otherwise, and RLS stays the real check). Comment bodies, author names, anchor labels and toast text are rendered as text only (a component test renders an `<img onerror>` body and finds no image).
- **Alternatives:** adding the thread to the list before the answer and removing it on failure; toasts for every failed action.
- **Why:** the pending pin already shows the user what will be created, and a second list state would have to be merged with the Realtime refetch.

## D-078 End-to-end suite for the comment loop

- **Chosen:** `tests/extension/comments.spec.ts` runs in its own Playwright project that depends on the older extension project, and runs its tests one after the other. The reason is the sign-in: the popup uses the e-mail code, Supabase allows one code per address per second, and the Mailpit helper clears the whole mailbox of an address, so two files that sign in the same seeded user at the same time would break each other. Each test uses its own page of the fixture site (`/p/<name>` is served by `index.html`, `spa.html` backs the `/spa/` routes with `spa.js`, which swaps the view and calls `history.pushState`), so threads never collide with the seeded ones on `/`, and removes the threads it created through the seeded owner (a password sign-in, no mail) in `afterEach`; the real-site test deletes its site row, which cascades to the threads. The scenarios: element comment with hover box, swallowed click, pin offset and restore after reload; text comment with Custom Highlight and adopted stylesheet; reply, edit and delete; orphaning when the element is removed; two single page app routes; two contexts (owner and member) live; guest, owner and live status changes; Escape handling and cursor; `https://example.com`. The e2e manifest got `https://example.com/*` in `host_permissions` next to the fixture hosts (the permission prompt cannot be answered, D-068), asserted by the manifest unit test, and the production guard now also rejects `example.com`. example.com no longer has an `h1` (it serves a single paragraph and a script that adds translations), so the test comments on its first paragraph; if the site is unreachable the test fails, it never skips. The seeded fixture page now shows "Comments, 3 open" on the launcher in the 3b enablement test.

## D-080 Mentions: body text, ids in `mentions`, one scanner

- **Chosen:** a comment body stays plain text. A mention is `@` plus the member's display name, inserted by the autocomplete, and the ids of the mentioned users go into `comments.mentions`. `@sitenote/core` has a `mentions` module with four pure functions. `findMentionQuery(text, caret)` finds an `@` at the start or after whitespace, with at most 40 characters up to the caret, no newline and no second `@`, and answers `null` for an out of range caret. `insertMention` replaces the query with `@Name ` and returns the new text and caret, and leaves the text unchanged when the range does not start at an `@`. `splitMentions(body, mentioned)` is the only scanner: at each `@` that does not follow a letter, digit, mark or underscore it tries the names longest first and accepts one only when the next character is not a letter, digit, mark or underscore either, then continues after the match, so a name that is a prefix of another ("Max", "Max Mustermann"), punctuation after a name, unicode names (the check works on code points, so astral letters count as word characters) and `ann@example.com` all behave. `mentionedIdsInBody` is derived from `splitMentions`, so what the composer submits and what the thread renders cannot disagree: deleting or editing the text drops the id on submit, and an id in `mentions` whose `@Name` is not in the body renders as plain text. Matching is case sensitive. People who share a display name are assigned in order of occurrence (the second `@Sam` is the second candidate). Segments are a discriminated union (`{ kind: "text", text }` or `{ kind: "mention", text, userId }`); nothing in the body is interpreted as markup, the renderer only decides which spans to highlight.
- **Alternatives:** storing mention ranges or markup tokens in the body (`@[id]`); case-insensitive matching; separate scanners for submit and render; a regular expression built from the names.
- **Why:** plain text keeps the body safe to render and to copy into ClickUp (design §9), and a single scanner removes the class of bugs where a user is notified for text that is not shown as a mention. Names with spaces rule out a "next word" regular expression, and building a regular expression from user controlled names is a needless injection surface.

## D-081 Mention normalisation and notification fan-out in the database

- **Chosen:** `20261021200000_mentions_and_notifications.sql`. `private.normalize_mentions(workspace, author, mentions)` runs from the `comments` insert trigger and from the update trigger whenever `mentions` changes: more than 20 ids is `23514` (counted before duplicates are removed, so a request cannot make the database scan an unbounded array), duplicates are removed keeping the first appearance, the author is removed, and every remaining id must be a member of the comment's workspace (`23514`, "mentions must be members of the workspace", as before). The stored limit moved from 50 to 20 (`comments_mentions_limit`) and the extension's `MENTIONS_MAX` followed. `private.comments_notify()` is an `AFTER INSERT` `security definer` trigger: every mentioned user gets a `mention`; every other participant (the thread creator and the distinct authors of non-deleted comments of the thread) gets a `reply`; the author is never notified, a participant who is mentioned gets only the `mention`, and users who are no longer members are skipped (so is a creator whose account was deleted, because `created_by` is null). Editing a comment does not notify anybody, so a typo fix cannot re-notify or spam; a mention added by an edit is stored and highlighted but silent. `notifications` joined the `supabase_realtime` publication with the default replica identity: clients subscribe with `user_id=eq.<uid>` and Realtime applies the existing `notifications_select` policy (recipient and current member). Clients read a notification with one embedded select (`threads(page_url, status)`, `comments(body, author_id, profiles!comments_author_id_fkey(display_name))`); the existing policies already allow every part of it for the recipient, which a test asserts, so the policy stays as it was. The seed now produces ten notifications as a side effect of its comments (nine replies and one mention), all unread.
- **Alternatives:** removing the author and deduplicating in the client only; notifying on edits; a separate fan-out table or a queue; a stricter limit check after deduplication; replica identity full.
- **Why:** the client is not trusted, and a mention of a non-member or a user outside the workspace must never produce a notification. One trigger keeps `mention` and `reply` exclusive per comment and per user, and recipients are computed from the state at insert time, which is what a reader of the thread would expect.

## D-082 Invite functions

- **Chosen:** `20261021200100_invite_functions.sql`, all in `public` with a pinned `search_path`. `create_invite(p_workspace_id, p_role, p_expires_in default '7 days')` is `security invoker`, so the existing `invites_insert` policy (owner only, `created_by = auth.uid()`) decides who may call it and a non-owner gets `42501`; it rejects the owner role and an expiry shorter than one hour or longer than 30 days with `23514` and returns the invite row including the token. It is executable by `authenticated` only. Owners could still insert into `invites` directly with any expiry (the column grants of D-034 stay), so the bounds are a guard for the UI path, not a security boundary: the owner is the party who decides how long their own link lives. `invite_preview(p_token)` is `security definer`, executable by `anon` and `authenticated`, and returns exactly one row: workspace name, role, expiry and `valid`; an unknown, expired or revoked token returns the same row with nulls and `valid = false`. `accept_invite(p_token, p_display_name default null)` is `security definer`, executable by `authenticated` only, and returns `{ workspace_id, role }`. It needs a signed-in user (`28000`), a valid token (`22023` with one message for unknown, expired and revoked), refuses an anonymous user a member invite (`42501`), and for an anonymous user requires a trimmed display name of 1 to 80 characters (`22023`) that replaces `profiles.display_name`; a registered user's profile is not touched. The membership is one `insert ... on conflict (workspace_id, user_id) do update` that keeps the higher of the existing and the invited role (`private.role_rank`: owner, member, guest), so the owner is never downgraded, a guest invited as a member is upgraded, a member invited as a guest stays a member, and two concurrent requests cannot create two rows. Invites are multi-use until they expire or the owner revokes them (`revoked_at`, already permitted), because the link is shared with a client team; each use is a separate membership. There is no extra brute force limit: a token is 24 random bytes (192 bits, D-033), and the failure answer is identical for every invalid token, so the preview endpoint reveals nothing an attacker can iterate on.
- **Alternatives:** a `security definer` `create_invite` with its own owner check; a single-use token; separate error codes per failure reason; a rate limit table; letting anonymous users accept member invites; deriving the guest name from the e-mail.
- **Why:** reusing the invoker path keeps RLS the only authorization for creation, while acceptance has to write a membership the caller may not insert, so it is the one place that needs `security definer`, with every rule written next to the write.

## D-084 Guest session handoff from the web page to the extension

- **Chosen:** refines design section 6 and D-043. On `/invite/[token]` a guest invite shows a name field. The page uses the cookie based browser client: it reuses an existing session or calls `signInAnonymously()`, calls `accept_invite(token, name)` with that session (the name is trimmed to 1 to 80 characters on the page and checked again by the function), lists the workspace's site origins with `sites` and only then starts the handoff, because the session is gone from the page afterwards. The handoff first sends `{ type: "external.ping" }` to the extension (`chrome.runtime.sendMessage(extensionId, ...)`, used only where `globalThis.chrome.runtime.sendMessage` exists, answered within 2.5 seconds or treated as missing, and `chrome.runtime.lastError` is read in the callback), and only after an `ok` sends `{ type: "external.session", accessToken, refreshToken }` taken from `getSession()` (which refreshes first when the token is close to expiry, so the proxy has no reason to rotate the refresh token afterwards). The extension (`src/external-router`, `src/session-handoff`, `runtime.onMessageExternal`) accepts exactly these two message types, validated with zod, and only from a sender whose URL origin equals the origin of `WXT_WEB_URL`; everything else answers `forbidden_sender` or `invalid_request`. The handoff refuses with `already_signed_in` when the extension holds a registered (non anonymous) user. Before it stores anything it verifies the tokens with a throw-away client that is never persisted (`getUser(accessToken)` must return an anonymous user, and a `members` read under that token must return at least one row), so a member's web session or a token without a workspace cannot be pushed into the extension (`session_rejected`); a network failure while checking answers `network`. Only then does it call `auth.setSession` and reply `{ ok: true, data: null }`. An existing anonymous session of the extension is replaced: a second invite link on the same browser starts a new guest identity and the old one stays in the database (its comments remain, the guest rejoins through any invite link). After `ok` the page calls `POST /auth/forget-session`, a route handler that deletes every cookie whose name starts with `sb-` and refuses (403) a request whose `Origin` header is not the configured web origin (so a foreign site cannot sign a visitor out of the web app); it never calls `signOut()`, which would revoke the session the extension now owns. If the cookies cannot be cleared the page still reports the connection and tells the guest not to use the web app with that copy. When the extension is missing the guest has joined and keeps the web session; the page shows install instructions (load unpacked during development, a store link placeholder text without a URL) and "I installed it — connect" repeats only the handoff. `already_signed_in` and other rejections keep the session and offer "Connect again". The extension id comes from `NEXT_PUBLIC_EXTENSION_ID` and defaults to the stable id of the manifest key.
- **Alternatives:** a handoff through a URL fragment or a custom protocol; giving the extension a fresh anonymous session of its own; calling `signOut({ scope: "local" })` on the page after the handoff; clearing cookies from client JavaScript; trusting the tokens without a probe; keeping a copy on the web and refreshing both.
- **Why:** Supabase rotates refresh tokens and revokes the family when one is reused, so exactly one party may own a session. `externally_connectable` messaging keeps the tokens off URLs and out of any page the extension does not control. The probe client makes the extension's own storage change only after the server confirmed the session is a guest of a workspace.

## D-085 `externally_connectable` and the production manifest guard

- **Chosen:** `createManifest` takes the web URL and writes `externally_connectable.matches = ["<origin of WXT_WEB_URL>/*"]`. The e2e build uses `http://localhost:3000/*` and `http://127.0.0.1:3000/*` regardless of the variable (the background still accepts only the origin of `WXT_WEB_URL`, which `pnpm db:env` sets to `http://localhost:3000`). `wxt.config.ts` and `wxt.e2e.config.ts` pass the manifest as a function reading `process.env.WXT_WEB_URL`, which WXT fills from `.env.local` before it resolves the manifest. When the variable is missing or not an http(s) URL the manifest simply has no `externally_connectable`, because `wxt prepare` runs in `postinstall` and must not fail on a fresh checkout. `scripts/assert-production-manifest.ts` now requires `externally_connectable` to be exactly the configured origin (from `WXT_WEB_URL` or `apps/extension/.env.local`) and no longer treats `localhost` inside that one key as forbidden; every other part of the manifest is still scanned for local hosts. The CI `checks` job sets `WXT_WEB_URL=https://app.sitenote.test` for its build and manifest check.
- **Alternatives:** throwing when the variable is missing; hard-coding the production origin; listing both loopback names in the production build.
- **Why:** a release built without the variable fails the guard instead of shipping an extension that silently cannot be connected, while installing dependencies keeps working everywhere.

## D-086 Invites in the web app

- **Chosen:** `/app/w/[workspaceId]/invites` is a dynamic server component. A visitor without a session is sent to sign-in with `next` set to the page; a malformed id, a non-member, a member and a guest all get 404 (a failed membership read throws instead, so an outage is not shown as a missing page). Only an owner sees the page, which lists every invite with role, creation and expiry time (UTC, formatted on the server) and a status computed from `expires_at` and `revoked_at` against one clock reading. The creation form offers the member and guest roles and 1, 7 and 30 days, and the server action re-validates all three, then calls `create_invite` (D-082) with an interval string; no UI path inserts into `invites`. "Copy link" writes `${NEXT_PUBLIC_WEB_URL}/invite/<token>` with `navigator.clipboard.writeText`; when that throws or the clipboard is missing, a focused read-only field with the link appears. "Revoke" updates `revoked_at` for an active invite of that workspace and says so when nothing matched. The link and the token are rendered only for active invites. The workspace row on `/app` links to the page for owners. `/invite/[token]` calls `invite_preview` first (a malformed token never reaches the database; the answer for any invalid token is the single message "This invite link is invalid or has expired."), then shows: a registered user "Join <workspace> as <role>" (server action calling `accept_invite` without a display name and redirecting to `/app`), a visitor or guest session with a guest invite the name form of D-084, and a visitor or guest session with a member invite "Sign in to join" to `/sign-in?next=/invite/<token>`. Database error codes map to fixed messages (`22023` invalid, `42501` member invite for an anonymous session, `28000` session ended, anything else generic). Both invite pages send `referrer: no-referrer` and the invite page is `noindex`, and links to site origins use `rel="noreferrer"` and only http(s) origins, so the token does not leak. `NEXT_PUBLIC_WEB_URL` became a required public variable (it was already written by `pnpm db:env` and listed in `.env.example`); `NEXT_PUBLIC_EXTENSION_ID` is optional.
- **Alternatives:** revoking the direct `INSERT` grant on `invites` so only `create_invite` can create rows (the 4a note): not done, because `create_invite` is `security invoker` (D-082) and would stop working, converting it to `security definer` would duplicate the owner check, and the expiry bounds are a guard for the UI and not a security boundary; building the link in the browser from `location.origin`; a client side data fetch for the list.
- **Why:** keeping the list, the bounds and the token on the server means a non-owner never receives a token, and RLS stays the only authorization.
